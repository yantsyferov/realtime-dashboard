# Realtime Market Dashboard

An Angular dashboard for simulated market data, generated by a custom AssemblyScript WebAssembly library running inside a Web Worker.

- [Live demo](https://realtime-dashboard-nine-swart.vercel.app/)
- [Source code](https://github.com/yantsyferov/realtime-dashboard)

## Requirements

- Node.js 22.x (locally built with 22.22.3)
- npm (the project declares npm 11.19.0)
- A modern browser with WebAssembly and Web Worker support

No backend, API keys, or environment variables are required.

## Install

```bash
git clone https://github.com/yantsyferov/realtime-dashboard.git
cd realtime-dashboard
npm ci
npm --prefix wasm-producer ci
```

The Angular application and the Wasm producer have separate package manifests and lockfiles. Both dependency sets must be installed.

## Run locally

Build the Wasm producer before starting Angular:

```bash
npm run build:wasm
npm start
```

Open http://localhost:4200/.

Angular changes are handled by the development server. After editing `wasm-producer/assembly/index.ts`, rebuild Wasm and reload the page so the worker loads the new module. `npm start` and `npm run watch` do not rebuild AssemblyScript automatically.

## Production build

```bash
npm run build
```

This builds the debug and release Wasm targets, then creates the Angular production build. The application loads the release module.

Publish the contents of `dist/realtime-dashboard/browser/`. The Wasm binaries are copied into its `wasm/` directory. Generated JavaScript bindings are imported by the worker during bundling.

## Tests

Build Wasm first, then run the Angular/Vitest suite once:

```bash
npm run build:wasm
npm test -- --watch=false
```

For watch mode:

```bash
npm test
```

The producer package also exposes Node's test runner:

```bash
npm --prefix wasm-producer test
```

This is a separate command and is not invoked by the root `npm test`. Check its output for discovered tests; a script declaration alone does not establish test coverage. Tests that execute the compiled producer require the preceding Wasm build.

## Architecture

| Location | Responsibility |
| --- | --- |
| `src/app/pages/` | Dashboard and producer settings UI |
| `src/app/market/` | Angular market service, settings validation, and metric calculations |
| `src/app/interfaces/` | Data and state interfaces |
| `src/app/worker/market.worker.ts` | Worker entry point and message wiring |
| `src/app/worker/market-worker-controller.ts` | Wasm loading, run lifecycle, and batch scheduling |
| `src/app/worker/worker-protocol.ts` | Commands and events exchanged with Angular |
| `src/app/worker/decode-batch.ts` | Conversion from packed numbers to market updates |
| `wasm-producer/assembly/index.ts` | Stateful price generation and seeded randomness |

The Angular service creates one worker and exposes application state through an RxJS `BehaviorSubject` and a read-only Observable interface. Components consume that stream with the async pipe.

The worker loads Wasm, generates batches on an RxJS `interval`, calculates cumulative metrics, and sends per-instrument snapshots to Angular. Generation and aggregation happen outside the UI thread. Navigating between pages keeps the active run alive.

The controller accepts message-sending and producer-loading functions as dependencies, allowing tests to substitute them without bootstrapping a real browser worker. Production uses the actual Wasm loader.

## Data and calculations

The Wasm generator retains a reference price per instrument. Each update changes that price by a small amount, generates a bid/ask snapshot, and simulates a trade at either the bid or ask. Seeded xorshift32 randomness makes sequences reproducible; it is not intended for cryptographic use.

Each update occupies seven entries in an `Int32Array`:

```text
[instrumentId, priceCents, tradeQuantity, bidCents, askCents,
 bidQuantity, askQuantity]
```

A batch of 100 updates therefore contains 700 integers. The same instrument can occur multiple times in a batch. The decoder processes every update before the worker sends an aggregated snapshot.

Generated prices use integer cents. Derived prices are rounded only for display.

| Metric | Calculation |
| --- | --- |
| Last price | Latest trade price |
| Spread | Latest ask price minus bid price |
| Volume | Sum of trade quantities since the run started |
| VWAP | Sum of price × trade quantity divided by cumulative volume |
| Imbalance | Latest (bid quantity − ask quantity) / (bid quantity + ask quantity) |

Book quantities do not contribute to trading volume. Volume starts at zero; unavailable metrics and zero-denominator results are represented by `null` and displayed as a dash. The application retains current per-instrument state rather than the full event history.

## Controls

| Setting | Default | Allowed range |
| --- | --- | --- |
| Instrument count | 5 | 1–50 |
| Updates per batch | 100 | 1–1,000 |
| Batch interval | 500 ms | 50–2,000 ms |

All settings must be integers. Updates per batch is the total across instruments.

- Editing settings does not affect the producer until Apply.
- Apply starts a new run and clears previous values and totals, including when paused.
- Pause cancels the timer subscription; Resume continues from the retained state without generating updates for the paused interval.
- Run IDs prevent results from an earlier run from replacing current UI state.
- Timer subscriptions are cancelled on pause, run replacement, and generation errors. The Angular service terminates its worker when destroyed.
- Settings and generated data are not persisted across reloads.

The requested interval is a scheduling target, not a hard real-time guarantee. Browser scheduling and processing time can delay batches.

## Deployment

The GitHub repository is connected to Vercel. Pushes to the production branch `main` trigger an automatic build and deployment.

The current `vercel.json` runs:

```bash
# Install
npm ci && npm --prefix wasm-producer ci

# Build and validate
npm run build && npm test -- --watch=false && npm --prefix wasm-producer test
```

A failing build or test command prevents the new deployment from being published.
Both the Angular/Vitest suite and the producer's Node.js tests must pass
before a new deployment is published.

The published directory is `dist/realtime-dashboard/browser`. A rewrite serves `index.html` for `/settings`, allowing Angular to handle direct visits and page refreshes on that route.
